# Architecture Decision Records (ADR)

このディレクトリには、本プロジェクトにおける設計判断の記録を置く。

## 目的

ADR は設計の正しさを証明するものではない。設計の良し悪しは将来の変更によってしか判定できず、その将来はまだ来ていないためである。

ADR の目的は、**後から間違いに気づいたときに、何が間違っていたかを特定できるようにすること**にある。そのため、決定の正当化よりも、検討した選択肢・却下理由・成立前提を反証可能な形で残すことを重視する。

## ステータス

| ステータス | 意味 |
|---|---|
| `Draft` | 記述済みだが、この方針での開発をまだ開始していない |
| `Active` | 実際にこの方針で開発を行っている |
| `Superseded by ADR-XXXX` | 別の ADR によって置き換えられた |
| `Deprecated` | 置換なしに廃止された（前提が消滅した等） |
| `Rejected` | 検討したが採用しなかった。記録として残す |

`Accepted` は用いない。単独開発であり承認者が存在しないため、承認を経た状態を意味する語を避ける。

Draft から Active への移行は、その方針に基づく最初のコミットが入った時点とする。

置換時は双方向にリンクする。新 ADR から旧を参照するだけでなく、旧 ADR のステータス行にも新へのリンクを記載する。

## ファイル構成

```
docs/adr/
├── README.md              # 本ファイル
├── _template.md           # フル版テンプレート
├── _template-lite.md      # ライト版テンプレート
└── NNNN-slug.md           # 各 ADR
```

ファイル名は 4 桁ゼロ埋めの連番と英小文字ハイフン区切りのスラグ。番号は欠番を作らず、廃止した ADR も番号を維持する。

## ライト版とフル版

判断の大半はライト版で足りる。フル版は構造を左右する判断に限る。

ライト版で書いた判断が後に覆ったり、より詳細な検討が必要になった場合は、フル版に書き直す。最初から完全を目指さない。

## ADR を書く条件

以下のいずれかに当てはまる決定を記録する。

- **変更コストが高い** — 後から覆すと他の箇所に波及する
- **選択肢が複数あった** — 却下案が書けない決定は ADR にならない
- **一見非合理に見える** — 半年後の自分が「なぜこうした」と問う決定
- **前提に依存している** — 条件が変われば誤りになる決定

実用上の目安として、**30 分以上迷った、あるいは比較検討した決定**は記録する。即決したものは記録しない。人間は悩んだ過程を忘れるため、迷いの痕跡そのものが記録の価値である。

**一度下した判断を覆したとき**は必ず記録する。何が間違っていたかが言語化されるため、最も価値が高い。

## ADR を書かないもの

- コーディング規約、フォーマッタ設定、命名、ディレクトリ名（リンタ設定や CONTRIBUTING が担当）
- 外部要因で一意に決まったこと（制約であって判断ではない。ただし制約下で何を選んだかは判断）
- 実装の詳細（コードとコメントが担当）
- 一時的な回避策（ただし恒久化しそうなものは記録する）

## 分量の目安

ADR が数十本に達すると誰も読まない。一覧を眺めて全体の設計思想が追える量が上限であり、本プロジェクトでは 10〜20 本程度を想定する。これを超える場合は記録基準が緩すぎる。

## 執筆

ADR は人間が書く。選択肢の列挙や考慮漏れの指摘に AI を用いることは妨げないが、**問い・却下理由・最終的な判断の言語化は人間が行う**。AI に全文を書かせると思考の過程が消え、記録としての価値が失われるためである。
